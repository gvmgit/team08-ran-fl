# GAPS.md - what did not work, what it limits, with numbers and run ids

Written to be read before the demo. Each item says which result it limits. Nothing here is hidden elsewhere: the evidence behind every number is in
`evidence/` and `node tools/rebuild.js` re-prints it with no AWS access.

## A. Task A (early-warning model)

| # | Gap | What it limits | Numbers and run ids |
|---|---|---|---|
| A1 | **The supplied data are saturated.** In both CSVs the single column `weak_ue_frac > 0.08` flags 99.999% (Site A) and 100% (Site B) of warning rows. Normal rows exceed 0.08 only at event minutes (10,145 rows, 0.256%). The warning label is effectively one threshold. | Any claim that federation improves the early-warning model on the supplied data. Local-only and central models already score AUROC 1.0000 on both sites, including the other site's data, and fire their first alarm at the earliest minute (median lead 120 minutes). | `ran-rescore-main-20261102T090733`: local-only and central AUROC 1.0000, F1 0.9988 to 1.0000, lead recall 100%. Federated DP: AUROC 0.9980 / 0.9997 / 0.9996 / 0.9983. An ablation without `weak_ue_frac` was offered and **not run** (decision of the team); it would be the right next experiment. **Four declared expectations of the main run are missed and shown as MISS by the rebuild:** local-only AUROC on the rare family was declared as expected at or below 0.85 and measured 1.0000 (A mobility, B congestion); and the declared "the federated model must beat local-only" fails (federated 0.9997 vs 1.0000 at A, 0.9996 vs 1.0000 at B). The same two comparisons pass in the stress run (0.9987 vs 0.2312, 0.9960 vs 0.1990). |
| A2 | **The federation effect is shown only in a constructed scenario.** We withheld each site's rare family from its own labels (Site A mobility, Site B congestion). This is a declared stress experiment, not the supplied data. | Generalisation: real sites may or may not look like this. | `ran-rescore-stress-20261102T090736`: local-only AUROC 0.2312 (A mobility) and 0.1990 (B congestion); central 0.9967 / 0.9875; federated DP 0.9987 / 0.9960. |
| A3 | **Federated is not better than central.** Federated AUROC is within 0.011 of central. The lead-time recall gap (federated 1.000 vs central 0.758 / 0.724) is mostly a threshold-choice effect, not better features. Federated precision on the withheld families is weak. | Any "federated beats central" claim. | Precision 0.795 (A mobility) and 0.598 (B congestion); F1 federated 0.879 / 0.739 vs central 0.600 / 0.626. |
| A4 | **One seed per model, autocorrelated windows.** The effective sample size is the number of events, not windows. | Confidence in small differences. | Example: 297 of 297 events warned gives a 95% Wilson lower bound of about 98.7%. No confidence intervals on AUROC. |
| A5 | **Per-window predictions are not kept** (1,036,800 windows per model and site). AUROC and F1 come from the grader's `results.json`; only the per-event records are kept and recomputed. | The offline rebuild recomputes lead-time recall, not AUROC or F1. | `tools/rebuild.js` checks the AUROC and F1 values against the manifest hashes only. |
| A6 | **DP accounting.** The framework counts each local epoch as one optimizer step; real steps are 1,417 per epoch. Our model code overrides the accountant to count real steps. Both choose noise multiplier 2.0, so the noise applied is the same; only the reported epsilon differs. | The epsilon figure (it is an upper bound from the RDP accountant over the real steps, not an end-to-end audit). | Reported 0.4268 (real steps, 8,502 steps, delta 1.9e-12) vs about 0.38 from the framework's own counting. Target was 1.0. |
| A7 | **Client DP log lines were dropped in the main and stress sessions.** The framework's log handler keeps INFO only from loggers named under `crosstrainer_training_client`; ours sat outside it. Fixed afterwards. | Evidence that the DP settings in force are the ones reported. | The grader recomputes the DP parameters deterministically from the same code and data (`evidence/TASK_A_MAIN_REPORT.md`). |
| A8 | **Model code at run time differed slightly from the repository copy**: the later logger name and a no-op stress switch. | Exact byte-for-byte reproducibility of the two Task A sessions. | `evidence/TASK_A_MAIN_REPORT.md`, last section. |
| A9 | **Task A records carry the re-grading job's run id, not the declaration's.** The Task A declarations are named after the baseline and session runs (`ran-local-only-...`, `ran-central-...`, `ran-fed-dp-...`, and the three stress runs). The per-event records and the scores were produced later by two re-grading jobs (`ran-rescore-main-20261102T090733`, `ran-rescore-stress-20261102T090736`), launched without a declaration of their own. So "one run id end to end" holds for the Task B grading runs (declaration, job, records and log lines all under the same `ran-nlm-regrade-...` id) but only through a mapping for Task A. For both tasks the federated sessions and the baseline jobs have a declaration and weights but no per-example records under their own run id (their outputs are weights in the transfer, NLM and models locations); the records of their models sit under the grading run that scored them, and `evidence/checks.json` and `judging.json` (`graded_in`) name which. | The "one run id" evidence check for Task A. | The mapping is `evidence/checks.json` (`runs`, `declaration` fields); the rebuild prints a note for both re-grading ids. |

## B. Task B (federated LoRA adapter)

| # | Gap | What it limits | Numbers and run ids |
|---|---|---|---|
| B1 | **Task B federated adapter: the first recipe was not stable; the fix recipe worked twice, but only at the last round, and only two sessions were run.** First recipe (3 rounds x 2 local epochs, learning rate 2e-4): two identical sessions gave a good adapter once and a congestion-only adapter once. We scored every intermediate global adapter (`ran-nlm-trajectory1-20261102T133915`): after aggregation 1 both answer "normal" for everything, after aggregation 2 both read mobility perfectly and miss most congestion, and the last round lands in different places. Fix recipe (6 rounds x 1 local epoch, same total local training, chosen after seeing the first recipe's test results): both sessions met the declared target (pooled 0.975 and 0.979). But in both, the global adapter still flips between families in rounds 3 to 5 (mobility only, congestion only, mobility only) and settles in round 6; no round 7 or 8 was run, so we do not know if that state persists. The cause (client drift vs averaging the two LoRA factors) is not isolated, and "fewer steps per round" was not separated from "more rounds". | Any claim that federated LoRA is stable for other round counts or other seeds; the fix result is for this recipe, these two sessions and a stop at round 6, on test text we had already seen. | First recipe `ran-nlm-fed-20261102T0911` 0.948 (A mobility 1.00, B congestion 0.89), `ran-nlm-fed-rep2-20261102T1149` 0.610 (0.00 / 1.00; declared target missed, MISS in the rebuild). Fix recipe `ran-nlm-fed-r6e1a-20261102T1350` 0.975 (0.97 / 1.00) and `ran-nlm-fed-r6e1b-20261102T1430` 0.979 (0.98 / 1.00), both met. Graded in `ran-nlm-regrade-20261102T121931`, `ran-nlm-regrade-r6e1a-20261102T144016`, `ran-nlm-regrade-r6e1b-20261102T170637`. |
| B2 | **Weak spots in the runs that worked.** First recipe, session 1: congestion 0.89 to 0.90 at both sites, mobility cause 0.65 (A) and 0.58 (B). Fix sessions: cause accuracy ranges from 0.51 (congestion cause at Site A, session 1) to 1.00 against 1.00 for central, and the adapter trained only on mobility text reaches 0.88 to 0.93 on mobility cause. Federated stays below central (0.975 and 0.979 vs 0.988). Action accuracy is 1.00 but the action follows deterministically from the cause, so it says little. | The strength of the Task B claim even in the best run. | `evidence/TASK_B_REPORT.md`. |
| B3 | **No differential privacy in Task B.** Only the Task A session runs `NN_HFL_WITH_DP` (epsilon 0.4268). Task B runs `NN_HFL`; Opacus on a 1.7B-parameter model was not attempted. The exchanged adapter is still protected by secure aggregation. | The privacy claim for Task B. | `ran-nlm-fed-20261102T0911` declaration, "not_claimed". |
| B4 | **A declared expectation was wrong: the untuned base is not near chance on mobility.** We declared at most 0.45 on Site A mobility; it scored 0.94 (Site B congestion 0.23, as expected). The base already reads mobility text, so federation's gain there is avoiding the forgetting local-only training causes, not beating the base. | Where the federated gain can be claimed (congestion and cause labels, not mobility). | `ran-nlm-baselines-20261102T090507`; MISS in the rebuild. |
| B5 | **The unseen family is absent by construction.** Each site's training and validation text has zero examples of the other family (generator setting `rare_fraction` 0); the test sets contain both. The supplied CSVs are not that lopsided (Task A). | Generalisation to real sites that log a few examples of the other family. | `evidence/taskb_test/corpus_manifest.json`. |
| B6 | **The task is easy and rule-made.** The generator derives alarms, cause and action from the counters with fixed rules, the prompt shows those counters and alarm names, and central training reaches 0.988. | External validity: a model that learns the generator's rules would look the same. | `taskb/make_text.py`, `DATA.md` section 2. |
| B7 | **In-client numbers cannot show cross-family quality.** Each client evaluates on its own validation text, which contains only its own family and normal text, so a global adapter that forgot the other family still scores well there. | Using the in-client progress numbers as a result. They are a progress signal only; the result is the offline grading. | `evidence/TASK_B_REPORT.md`, in-client table. |
| B8 | **Re-grading changed a few counts for run 1's federated adapter.** Four adapters reproduce exactly. For run 1's adapter, Site A congestion is 90/100 instead of 89 and a few cause counts move by one to four examples (same file, same code, a different GPU instance; we read this as numerical differences on near-tied candidates and did not investigate). The per-example records are the reported numbers, as declared before the re-grading. | Exact repeatability of scoring on a different instance. | `ran-nlm-fed-score-20261102T093824` (first scoring) vs `ran-nlm-regrade-20261102T121931`; shown as "DIFFERS (disclosed)" by the rebuild. |
| B9 | **Only two federated runs and one seed per baseline.** | Confidence in every small difference. | Pooled 95% intervals in `evidence/TASK_B_REPORT.md`; they do not cover run-to-run variation. |
